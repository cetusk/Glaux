# 完成した曲からパートを起こす: 研究・ツールの調査(2026-10-14)

目的: 好きな曲の譜面が手に入らないとき、耳コピの代わりに、曲の音声ファイル(wav・mp3・m4a / mp4 など)から
各パートを **譜面(MIDI)・音源・音色・ミックスまで含めて** 起こし、練習・研究・アレンジ(カバー)に使えるようにする。
その前段として、必要になる研究・ツール・製品・評価の方法・法的な枠組みを広く調べた。

調べ方: 6 つのテーマ(音源分離 / 音程のある楽器の譜起こし / ドラムの譜起こし / 曲の骨組み〈拍・テンポ・調・和音・構成〉 /
音の再現〈楽器・音色・奏法・ミックス〉 / 製品・評価・法律)を並行して Web で調べた。tract で動くかどうかは、
公開されている ONNX の一部を実際に tract-onnx 0.23.8 に読み込ませて確かめた(4.5 節)。

**注意**
- ライセンス・精度の記述は各出典に基づくが、**採用の前に、各リポジトリの LICENSE と重みの配布条件を必ず確かめ直すこと**。
  コード・学習済みの重み・学習データのライセンスは別々で、食い違っていることが多い。
- 「推測」と書いたものは調査者の見立てで、出典はない。
- 調査の途中で Web 検索の回数の上限に達したため、後半は URL の分かっている一次資料を直接読んで補った。
  確かめきれなかった点は 12 章にまとめた。
- 論文ごとに評価データ・クラスのまとめ方・指標の算出方法が違うので、**数字を横に並べて比べられない**ことが多い。

採用の条件(Glaux の方針): GPL / AGPL のコードはリンクしない。非商用(NC)の重みは同梱しない。一般的な CPU で動く。
Rust から使える(純 Rust の実装、または ONNX を tract で推論)。Python に頼るのは任意の外部連携だけ。

## 0. 要約

1. **完成したミックスから全パートを正確に起こせる製品・研究は、まだ無い。**
   実在のポップスで全楽器を起こすと、最新の研究でも音の一致(立ち上がり・音高・楽器名)は 2〜3 割にとどまる
   (MulTTiPop で Onset F1 約 29、MuScriptor 論文の RWC-Pop で Multi F1 25.6)。合成音源(Slakh2100)では 7〜8 割に届くので、
   **合成データと実在の録音の差**が最大の壁になっている。製品のレビューも「単一の楽器は良いが、多楽器・ドラム・リズムと拍子が弱く、
   手直しが前提」で一致している。
2. **楽器ごとに分けた音(stem)からなら、精度はずっと高い。** 正解の stem での譜起こしは F1 0.9 前後に届く(Harmonica、2026)。
   したがって骨組みは **分離 → パートごとに専用の譜起こし → 統合** が現実的。ただし分離の質がそのまま上限を決め、
   ギター(約 9 dB)・ピアノ(約 8 dB)・「その他」は、歌・ベース・ドラム(11〜15 dB)より明らかに低い。
3. **ライセンスの壁が厚い。** 性能の高い多くのモデルが、重みが非商用・研究用・出所不明、またはコードが GPL。
   Demucs の重みも作者が「研究目的のみ」と明言している。同梱できるのは一部で(下の表)、残りは
   「使うときに公式の置き場から取得」「利用者が入れた外部ツールと連携」「権利のきれいなデータで自前に学習」のどれかになる。
4. **同梱・取得の候補になるもの**(コードと重みがともに MIT / Apache / CC BY 表記。要確認を含む)
   | 段 | 候補 |
   |---|---|
   | 拍・小節頭 | Beat This!(同梱済み)+ madmom の DBN をコードから移植(コードは BSD) |
   | 和音(転回形まで) | Jiang ら 2019、consonance-ACE 2025 |
   | 調 | S-KEY(約 325KB) |
   | ピアノ | Transkun V2(ONNX が tract で動くことを確認)、Kong ら(重み CC BY 4.0) |
   | 歌・ベース | 分離した stem に SwiftF0(同梱済み)をかけて音符に区切る |
   | ギター・その他 | 分離した stem に basic-pitch(同梱済み) |
   | ドラム | 完成品は無い → E-GMD / StemGMD(CC BY 4.0)で小さな CRNN を自前で学習 |
   | 分離 | 最高水準で同梱できるものは無い → 取得型(Mel-RoFormer など、重みの条件を要確認)か外部連携、将来は自前の学習 |
5. **Glaux ならではの強みが 2 つある。**
   - **鳴らして比べられる。** 起こした MIDI に音源を当てて書き出し、原曲(または分離した stem)と比べて直す
     「分析と合成の往復」は、DAW である Glaux が最もやりやすい。熟練者の耳コピも「書いた音を鳴らして原曲と聴き比べる」のが中心。
   - **ミックスの逆算の前提がそろう。** ミックスの逆算の研究(ゲイン・パン・EQ・コンプ・リバーブの推定)は「加工前の素材」と
     「完成ミックス」の組を前提にしている。作り直したトラックの加工前の音は Glaux が自分で鳴らすので、正確に分かる。
6. **評価は 3 層で行う。** 自前で書き出した合成データ(回帰テスト・調整用)/ Slakh2100(CC BY 4.0)/
   実在のポップスの評価セット MulTTiPop(CC BY 4.0、評価専用)。最終の判断は実在の録音で行う。
7. **法的には**(日本、法律相談ではない): 手元のファイルを自分の PC で起こして練習・研究・編曲に使う範囲は、
   私的使用(著作権法 第 30 条・第 47 条の 6)で説明しやすい。起こした譜面・MIDI・カバーを公開するときは、
   編曲・原盤・出版の許諾が別に要る。YouTube の URL から音声を取り込む機能は YouTube の規約とぶつかる。
8. **方針**(11.1 節): Glaux は作曲のソフトで、この機能は副次的なもの。小さくライセンスのきれいなものだけを同梱し、
   分離や大きなモデルは利用者がライセンスを確かめて取得する。自前の学習は保留。

## 1. 全体の流れと、どこが難しいか

| 段 | すること | 今の到達点(実在の曲) | 難しさ |
|---|---|---|---|
| 読み込み | wav / mp3 / m4a / mp4(AAC)/ flac / ogg を読む | 済(symphonia) | mp3 128kbps などの圧縮は分離の品質の上限を下げる |
| 骨組み | 拍・小節頭・テンポマップ・拍子・チューニング・調・和音・構成 | 拍は F1 約 0.89、小節頭は約 0.78(GTZAN)。和音の majmin は約 0.8 | 小節線が途中で 1 拍ずれること、2 倍 / 半分のテンポ、変拍子 |
| 分離 | 歌・ベース・ドラム・ギター・ピアノ・その他 | 歌・ベース・ドラム 11〜15 dB、ギター 9、ピアノ 8、その他 8.7(最上位、Multisong) | 「その他」の中の楽器(シンセ・弦・管)は分けにくい。ライセンス |
| 譜起こし(音程) | stem ごとに音符にする | 正解の stem なら F1 0.9 前後。ミックスから全楽器を直接起こすと 2〜3 割 | 分離の漏れが「幽霊の音符」を生む。オクターブの誤り。音の終わり |
| 譜起こし(ドラム) | キック・スネア・ハイハット・タム・シンバル + 強さ | 5 クラスで F1 約 0.8(ミックスから)、ドラムだけなら約 0.9 | シンバルの区別、ハイハットの開閉、ゴーストノート。同梱できるモデルが無い |
| 音の再現 | 楽器の種類・音源の選択・音色のつまみ・奏法・強さ | 研究の多くは単音が前提で、にじみ入りのフレーズからの推定はまだ | 分布の外の音で精度が大きく落ちる |
| ミックス | トラックごとのゲイン・パン・EQ・コンプ・空間 | 加工前の素材があれば推定できる(研究) | GPU で 1 曲 30 分以上かかる研究もある。CPU 向けには絞り込みが要る |
| 確かめる | 起こした結果を原曲と比べて直す | 製品は手直しが前提 | 何を「正解」とするか(人どうしでもコードの付け方は割れる) |

## 2. 音源分離

### 2.1 最高水準とその推移

| モデル | 年 | 構造 | 平均 SDR(MUSDB18-HQ、dB) | 出典 |
|---|---|---|---|---|
| Spleeter | 2019 | U-Net | 5.91 | https://arxiv.org/html/2309.02612v2 |
| HDemucs(v3) | 2021 | 波形とスペクトログラムの併用 | 7.68 | 同上 |
| HTDemucs(v4) | 2022 | 併用型 + Transformer | 9.00(疎な注意で 9.20) | https://github.com/facebookresearch/demucs |
| BS-RoFormer(12 層、追加データ 500 曲) | 2023 | 周波数の帯域ごとに分けて RoPE 付き Transformer | **11.99**(歌 12.72 / ベース 13.32 / ドラム 12.91 / その他 9.01) | https://arxiv.org/html/2309.02612v2 |
| Mel-RoFormer(6 層) | 2023 | メル尺度の帯域 | 9.64 | https://arxiv.org/html/2310.01809 |
| SCNet | 2024 | 疎な圧縮 | 9.00(large 9.69) | https://arxiv.org/pdf/2401.13276 |

- 2019〜21 年は U-Net / LSTM、2021〜22 年は Demucs、2023 年以降は帯域分割の RoFormer が主流。SDX'23 の首位は平均 9.97 dB で、
  2021 年(8.33 dB)から 2 年で約 1.6 dB 伸びた(https://arxiv.org/abs/2308.06979)。SDX'23 は「学習データの誤り・漏れ込み」が主題だった。
- コミュニティの評価(MVSEP の Multisong): 公開されている 6 パートの最上位「BS-RoFormer SW」は
  歌 11.30 / ベース 14.62 / ドラム 14.11 / ギター 9.05 / ピアノ 7.83 / その他 8.71 dB(https://mvsep.com/news/64)。
  元のパートを mp3 128kbps にしただけで平均 21.68 dB まで下がるので、**圧縮された入力では SDR に天井がある**
  (https://mvsep.com/quality_checker/multisong_leaderboard)。
- 生成型の「何でも分離」も出てきた(Meta の SAM Audio、2025-12)。ただし論文自身が「プロの音楽のデミックスでは専用モデルの方がまだ上」と書いており、
  GPU 向けの大きなモデル(5 億〜30 億パラメータ)なので Glaux には重い(https://arxiv.org/html/2512.18099v1)。

### 2.2 4 パートより細かい分離

| 対象 | 候補 | 状況 |
|---|---|---|
| ギター・ピアノ | BS-RoFormer SW、htdemucs_6s | 6s は公式が「実験的。ピアノは漏れ込みと雑音が多い」(https://github.com/facebookresearch/demucs) |

### 2.3 Glaux で動かせるか

| モデル | 重みの大きさ | CPU の速さ(出典どおり) | 3〜4 分の曲の見積もり(推測) |
|---|---|---|---|
| htdemucs(ONNX) | fp32 316MB / fp16 166MB | 実時間比 0.20(M4 Pro、https://huggingface.co/adowu/htdemucs-onnx) | 約 1 分 |
| Mel-RoFormer(歌) | fp16 464MB | 8 秒の区間あたり約 9 秒(ORT、https://huggingface.co/audiojs/mel-roformer) | 約 8 分(重ね合わせ 50%) |
| BS-RoFormer SW(6 パート) | fp16 336MB | 公表値なし | 5〜15 分 |

- ONNX では複素数の STFT がネックなので、**STFT / iSTFT はグラフの外で行い、時間の長さを固定して書き出す**のが主流
  (https://mixxx.org/news/2025-10-27-gsoc2025-demucs-to-onnx-dhunstack/ 、https://huggingface.co/silverdaw/bs-roformer-rhythm-onnx)。
  glaux-ml が今やっている「rustfft で変換して tract で推論」と同じ形で組める。
- tract-onnx 0.23.8 のソースでは STFT / DFT / Einsum / LayerNormalization / RMSNormalization / Attention / RotaryEmbedding が登録されている(`Loop` は無い)。
  1 億パラメータ級の Transformer で ORT より遅い可能性はある(推測)ので、遅ければ `ort` を任意の機能にする。
- 純 Rust / C++ の移植: demucs-rs(Burn、Apache-2.0、GPU 前提)、demucs.cpp(MIT、CPU で省メモリ)。

### 2.5 品質を上げる工夫と、譜起こしへの影響

- 複数モデルの合成(波形の平均が安定)、推論時の水増し(左右の入れ替え・位相反転)、区間の重ね合わせ(線形フェード)。
  SW を 75% 重ね合わせ + TTA にすると平均 13.25 → 13.36 dB(https://mvsep.com/quality_checker/multisong_leaderboard)。
- 分離と譜起こしを一緒に学習すると両方が良くなる(Jointist: 分離 +5 dB、譜起こし +1 ポイント、https://arxiv.org/abs/2302.00286)。
- 推測: 漏れ込みは「幽霊の音符」を生むので、パートの音量の小さい区間を捨てる・元のミックスと照らし合わせる、といった対策が要る。
  歌とベースは分離の品質が高く単音なので、単音の音程推定と組むのが最も確実。

## 3. 曲の骨組み(拍・テンポマップ・拍子・チューニング・調・和音・構成)

### 3.1 拍・小節頭・テンポ

| システム | 精度(GTZAN など) | コード | 重み | 備考 |
|---|---|---|---|---|
| **Beat This!**(ISMIR 2024、同梱済み) | 拍 F1 89.1 / 小節頭 78.3。small は 88.8 / 77.2 | MIT | **MIT**(明記) | https://arxiv.org/abs/2407.21658 |
| Beat This! + DBN | 小節頭の連続性 CMLt 67.3 → **73.3**、AMLt 79.1 → **87.8** | ― | ― | 同上(論文 Table 2) |
| madmom | ― | BSD | **CC BY-NC-SA 4.0** | DBN は学習済みファイルを持たないコード部分 |
| allin1(拍・小節頭・区間を同時に) | Harmonix で拍 F1 .958、小節頭 .915 | MIT | MIT | htdemucs と NATTEN が前提(https://arxiv.org/abs/2307.16425) |
| BeatNet+ | 打楽器の少ない曲に強い | なし | なし | ライセンス未設定 |

- テンポマップには「小節線が途中で 1 拍ずれない」ことが F1 より大事(推測)。**madmom の DBN を Rust に移植して、
  Beat This! の出力確率にかける後処理**が最も費用対効果が高い。
- 拍子: 4 拍子の曲に 2 拍子の小節が 1 つ挟まると小節頭の周期が崩れる(Beat This! の論文)。
  Logic の Smart Tempo も拍子の変化の検出には利用者のヒントが要る(https://support.apple.com/kb/HT208458)。
- スウィング比: 分離したハイハット・ライドの打点が拍の中のどこに落ちるかで求まる(Dittmar ら ISMIR 2015、
  https://publica.fraunhofer.de/handle/publica/408120)。
- テンポの揺れの大きさから「打ち込み / クリックありの生演奏 / クリックなし」をある程度見分けられる
  (https://theory.esm.rochester.edu/integral/?p=9705)。

テンポマップの作り方(推測):
1. 拍と小節頭を求める(必要なら DBN を通す)。
2. 拍の番号と時刻を直線で当てはめ、ずれが小さければ一定テンポ 1 つで表す。
3. ずれが大きければ区切りを探して区間ごとに当てはめ、小節単位でテンポ変更を置く。自由な揺れなら拍ごとに置く。
4. 最初の小節頭を 1 小節目の頭とし、それより前は弱起として扱う。
5. 小節頭どうしの間の拍数で小節ごとの拍子を決め、多数決でまとめる。例外の小節は拍子変更として残す。
6. 2 倍 / 半分の誤りと拍子は利用者が直せるようにし、「小節頭の確からしさ」を保存して疑わしい所を示す。

### 3.2 チューニングのずれ

A=440Hz から外れた曲は、和音・調・音符のモデルに入れる前に補正が要る。スペクトルの山の周波数を 100 セントで割った余りの
ヒストグラム(librosa の `estimate_tuning` と同じ考え方、https://librosa.org/doc/main/generated/librosa.estimate_tuning.html)
か、分離した歌・ベースの細かい音高で求められる。追加のモデルは要らない。

### 3.3 和音

| モデル | 語彙・転回形 | コード | 重み | 判定 |
|---|---|---|---|---|
| **Jiang ら**(ISMIR 2019) | 根音・三和音・**ベース**・7th〜13th を分けて予測し、HMM で解読 | MIT | 同梱(5.7MB × 5)| 候補 |
| **consonance-ACE**(ISMIR 2025) | 根音・**ベース**・構成音を別々に予測。Beat This! で拍に合わせる機能あり | MIT | 同梱(57.6MB) | 候補 |
| BTC(ISMIR 2019) | 170 種、転回形なし | MIT | 同梱。ただし第三者が CC BY-NC-SA と主張 | 要確認 |
| ChordFormer(2025) | 大語彙 | 未公開 | 未公開 | 使えない |
| Chordino / NNLS Chroma | ― | GPL | ― | 使えない(論文から自前で書き直す余地はある) |
| madmom・Essentia のモデル | ― | BSD / AGPL | 非商用 | 使えない |

- 公表スコアの例(consonance-ACE の論文、RWC Pop + USPop): Root 84.0 / MajMin 77.8 / Sevenths 66.0 / Tetrads 60.8
  (https://arxiv.org/html/2509.01588)。データも分け方も論文ごとに違うので、横に並べて比べられない。
- 転回形: 2 つの候補はどちらもベース音を独立に出すので、**分離したベースの拍ごとの最低音**と組み合わせれば精度が上がる(推測)。
- 人どうしでもコードの付け方は割れる。Billboard の 50 曲を 4 人の熟練者が独立に付けると、区切り方と構成音の両方でよく一致しない
  (CASD、https://github.com/chordify/CASD)。UI では候補を並べて選ばせる方が合う(推測)。

### 3.4 調と転調

| モデル | MIREX スコア(FMAKv2 / GTZAN / GiantSteps) | コード | 重み |
|---|---|---|---|
| **S-KEY**(Deezer、ICASSP 2025) | 73.2 / 74.4 / 72.1。ONNX で約 325KB | MIT | 同梱(条件の別記なし、要確認) |
| madmom の CNN | 73.1 / 67.9 / 71.0 | BSD | 非商用 |
| libKeyFinder / Essentia | ― | GPL / AGPL | ― |

S-KEY は曲全体で 1 つの調を出す(https://arxiv.org/html/2501.12907v2)。転調は、窓をずらしながらかけて調の確率を HMM でなめらかにし、
和音の列から求めた調と照らし合わせる(推測)。

### 3.5 構成と、繰り返しをまとめて精度を上げる工夫

- allin1(MIT / MIT)は Harmonix で HR.5F .660。最新の SongFormer はそれを明らかに上回るが、特徴の抽出に使う MuQ の重みが
  CC BY-NC なので全体として非商用(https://arxiv.org/html/2510.02797v2)。
- **繰り返す区間の特徴を平均してから和音を推定すると、認識精度も区切りの忠実さも上がる**(Mauch ら ISMIR 2009、
  https://ir.webis.de/anthology/2009.ismir_conference-2009.36)。サビの繰り返しを束ねて歌詞の書き起こしを 1 つにまとめる例もある
  (McVicar・Ellis・後藤 ICASSP 2014、https://staff.aist.go.jp/m.goto/PAPER/ICASSP2014mcvicar.pdf)。
  推測: 構成解析で同じ記号の区間を小節単位でそろえ、和音・音符の確率を平均してから解読すれば、耳コピの代わりとしての品質に効く。

### 3.6 基盤モデル(MERT・MuQ・MusicFM など)

小節頭と構成には効くが、和音と調では専用の小さなモデルに負ける(MusicFM の論文、https://arxiv.org/html/2311.03318)。
3 億パラメータ級で、MERT と MuQ の重みは非商用。今の Glaux で採用する理由は薄い。MusicFM(MIT タグ)だけを将来の候補に残す。

## 5. ドラムの譜起こし

### 5.1 課題の整理

- ドラムだけの録音(DTD)、ほかの打楽器がある録音(DTP)、旋律楽器と歌の入ったミックス(DTM)の順に難しい
  (Wu ら 2018 の総説、https://musicinformatics.gatech.edu/wp-content_nondefault/uploads/2018/05/Wu-et-al.-2018-A-review-of-automatic-drum-transcription.pdf)。
- **精度を下げる最大の要因はほかの楽器の音。** 同じデータ・同じモデルで DTD は F1 0.91、DTM は 0.78
  (Weyers ら ISMIR 2025、https://www.audiolabs-erlangen.de/content/05_fau/professor/00_mueller/03_publications/2025_WeyersUML_LimitationsADT_ISMIR_ePrint.pdf)。
- **クラスを増やすほど下がる**(STAR Drums、MDB): 3 クラス 0.81 → 5 クラス 0.79 → 8 クラス 0.75 → 18 クラス 0.67
  (https://transactions.ismir.net/articles/244/files/6888ab991b2f2.pdf)。弱点はシンバル(クラッシュとライドの区別)・タム・ハイハットの開閉。
  シンバルは正解を付けた人どうしでも意見が割れる(https://ismir2024program.ismir.net/poster_68.html)。
- 電子音楽中心の RBMA13 は、どのモデルでも最低の成績。

**良かった組み合わせ**: ①ドラムを分離 → ②一体の ADT(5 クラス)→ ③部品ごとの分離音は「クラスの細分化」と「強さの推定」だけに使う。
部品分離から直接立ち上がりを拾う方式は、一体の ADT より成績が下だった。NMF だけでは実用の水準に届かない。

### 5.3 後処理(自前の DSP で組める)

- 強さ: 部品ごとの分離音のラウドネスを立ち上がりの前後 50ms で最大値に取り、0〜127 に写す(Riley &amp; Dixon)。
  強さを当てると、分類の数字が同じでも聴いたときの質がはっきり上がる(聴き比べで 919 勝 対 677 勝、https://arxiv.org/pdf/2004.00188)。
- ハイハットの開閉: 次の音まで(最長 150ms)の音量の最小値が最大値の 75% より上なら「開」。クラッシュとライドは減衰の長さで振り分ける。
- ゴーストノート・フラム: 直接扱う研究は見つからなかった。推測: ゴーストノートは分離したスネアの強さの分布の下の山、
  フラムは「同じクラスの立ち上がりが 15〜50ms 以内に 2 つ」として拾う。
- 拍への揃え: 拍に同期させるモデルは拍の推定誤りで逆効果だった(ADTOF の論文)。推測: 立ち上がりは絶対時刻のまま持ち、
  「グリッドへの写像 + ずれ量」の 2 層にして、揃える度合いを選べるようにする(グルーヴを残す)。
- 語彙の外の打楽器(シェイカー・コンガなど): 数例を与えるだけで拾える few-shot の ADT がある(https://arxiv.org/pdf/2008.02791)。
  推測: 「波形上で 2〜3 打を指すと同じ音を全部拾う」UI と相性が良い。
- 808 キックの音程: 専用の研究は確認できず。推測: キックと判定した区間に SwiftF0 をかけて音程と下降を推定する。

### 5.4 Glaux での見立て

同梱できる完成品の ADT モデルは、ほぼ見当たらない。**E-GMD(444 時間・43 キット・強さ付き)と StemGMD(9 部品の分離音)、
どちらも CC BY 4.0 で、小さな CRNN(BiGRU)を自前で学習し、ONNX にして tract で動かす**のが本命(ただし自前の学習は当面保留。11.1 節)。
tract は ONNX の GRU / LSTM / Scan に対応している(https://github.com/sonos/tract/tree/main/onnx/src/ops/rec)。
到達目標は、ADTOF を手元で比較の基準に使い(配布はしない)、5 クラスで MDB 0.8 前後。

## 6. 音の再現(楽器の種類・音色・奏法・ミックス)

### 6.1 楽器の種類

|---|---|---|

推測:
- 系統を絞ってから(CLAP か自前の小さな分類器)、その系統の GM 音色・SFZ・CLAP のプリセットを**その stem から起こした音符で鳴らして**、
  stem と比べて並べる。単音ではなく同じ音符で比べるので、音域による音色の変化や強さの差も比較に入る。
- シンセの種類(pad / pluck / lead / スーパーソウ / 808)の標準データは無い。記述子のルール(立ち上がり・減衰、うなり、左右の相関、
  30〜60Hz の基音と下降)と、CLAP の埋め込みを入力にした自前の分類器を組み合わせる。

### 6.2 音色のつまみの推定

- 研究のほとんどは**単音**が前提で、分布の外の音では大きく落ちる。Hayes ら(Surge XT、ISMIR 2025)も対象は単音と明記
  (https://arxiv.org/html/2506.07199v1)。「分離してから変換」すると分離の傷がそのまま伝わる(https://arxiv.org/pdf/2605.09259)。
- 「つまみの値どうしの差で評価すると誤解を招く(同じ音になる別の組が多い)。音で評価すべき」(Hayes ら)。
- 損失は音源の種類で選ぶ: subtractive にはスペクトログラム系、音量の揺れには時間を揃えた包絡、加算合成には JTFS。
  自動の指標と聴取の順位は 16 件中 3 件で食い違う(https://arxiv.org/html/2506.22628v2)。
- 時間変化は、低域通過で滑らかにした曲線として取り出すのが「合い方と読みやすさ」の釣り合いが最良(https://arxiv.org/html/2510.06204v1)。

推測(この機能の中心課題への進め方):
1. **音符を条件にした合わせ込み**: 候補の音を単音ではなく、起こした MIDI でフレーズごと鳴らし、stem と同じ時間軸で比べる。
2. **にじみの重みづけ**: 自分の音符の倍音の近くは重く、ほかのパートのエネルギーが大きい所は軽くする(SDX23 の損失マスクと同じ考え方)。
3. **目立つ所を選ぶ**: ほかのパートが静かで、その楽器が単独で鳴っている区間を探して重く扱う。
4. つまみは曲全体で 1 組に固定し、カットオフや音量だけを滑らかな曲線として追加で合わせる。

### 6.3 曲そのものから音を切り出す

- ミックスからキック・スネア・ハイハットの単発音を生成する DOSE(コード Apache-2.0、重みの条件は要確認、https://github.com/HSUNEH/DOSE)。
- ドラム音の検索: 混合音と単発音を同じ埋め込み空間に置く(Kim &amp; Nam AES 2020)。CLAP の埋め込みの重心でサンプルライブラリに
  クラスを付けた例(ADT_STR)。
- 推測: ドラムの stem を立ち上がりで切る → 埋め込みでまとめる → ほかの音と重ならない 1 打を選ぶ → サンプラーの楽器にする。
  ループは、小節単位の自己相似が非常に高いときに 1 小節を切り出す。学習不要で Rust だけで作れる。

https://arxiv.org/pdf/2410.21233 、https://github.com/mhrice/RemFx 、https://www.ee.columbia.edu/~dpwe/papers/Aven03-unmix.pdf

推測(Glaux での組み立て): 作り直したトラックの加工前の音は Glaux が鳴らすので、研究と同じ「加工前の素材 → stem / 原曲」の形になる。
1. ゲインとパン: 帯域ごとに最小二乗法で解き、パンは Avendano の指数で初期値を決める。
2. EQ: 周波数特性の計算だけで最適化に当てはめる(音を通さないので速い。参照曲に寄せるマスタリングと同じ方式)。
3. コンプ: 波高率・ラウドネスの幅・音量の包絡の差で合わせる。
4. リバーブとディレイ: 音の終わりの後の減衰から長さ、残りの自己相関から遅れの時間を出す。
5. 最後に全トラックの和を原曲と比べ、L/R/M/S の多重解像度 STFT で一緒に微調整する。

### 6.6 作り直しの評価

| 指標 | 使いどころ | 注意 |
|---|---|---|
| 多重解像度 STFT / メルの距離(stem ごと、L/R/M/S) | 主な指標 | SI-SDR は不向き |
| CLAP のコサイン類似度 | 音色の印象の近さ | ― |
| FAD / KAD | 区間の集まりどうしの比較 | 1 曲だけでは区間をたくさん集める必要がある(推測) |
| 音符の F1(楽器も一致) | 譜起こしの段 | 楽器名の誤りで大きく下がるので、粗い分類の F1 も並べる |
| 聴取 | 最後の判定 | 自動の指標と食い違うことがある |

推測: 段を分けて段ごとに指標を持ち(音符 → 楽器 → 音色 → 表情 → ミックス → マスター)、観点ごとの差を数値で AI に返す
(例:「Pad の 2〜4kHz が原曲より 3dB 少ない」「Lead の残響が 0.4 秒短い」)。AI は差の大きい観点から直し、最後にミックス全体で確かめる。

### 8.2 指標

- 音符: `mir_eval.transcription`(立ち上がり 50ms・音高 50 セント、音の終わりは長さの 20% と 50ms の大きい方まで)。

### 8.3 DAW の曲を書き出して正解を自作する方法

- 先例: Slakh は「MIDI を音源で書き出し、パートと MIDI を正解にする」方式そのもの。MuScriptor はこれを 145 万曲 × 250 以上の音源で行った。
- **落とし穴**: 合成だけで学んだモデルは実在のポップスで大きく落ちる(YourMT3+、MulTTiPop、MuScriptor の各論文)。
  推測: 書き出したデータには、市販の音源のミックスの処理・マスタリングの音圧・演奏の揺れ・重ね録り・複雑な変調が無い。
  同じ音源で書き出したものを評価にも使うと「自分の音源に強い」偏りが出る。
- 実在の録音に正解を付けるのも難しい。MulTTiPop では、音声と MIDI の時刻合わせに使えた区間が 49.1% だった。
- 推測: 評価は 3 層にする。(a) 自前で書き出したデータ(Glaux の内蔵音源・SoundFont・CLAP × Lakh MIDI。音源・効果・音圧を振る)で
  回帰テストと調整、(b) Slakh で他の研究と比べる、(c) MulTTiPop と実在の録音で最終の判断。

## 11. Glaux での構成案(推測を含む)

### 11.1 位置づけと方針(2026-10-14)

- **Glaux は作曲のソフトで、曲から起こす機能は副次的なもの**(「必要なら起こすこともできる」程度)。
  専用の画面・モードは作らず、読み込みの 1 項目と AI の道具から始め、結果は普通のトラックとしてタイムライン・ピアノロールで直す。
  確認に使う「原曲との聴き比べ・遅い再生・区間の繰り返し」は、作曲でも参考曲と聴き比べるのに使える一般の機能として作る。
- **同梱するのは、ライセンスがきれいで小さいものだけ**(拍・調・和音など)。アプリの大きさを大きく増やさない。
- **分離や大きなモデルは、必要になったときに利用者がライセンスを確かめて取得する。** Glaux は配布元とライセンスの表記を示し、
  入れる場所と読み込み方を用意するだけで、重みを再配布しない。外部ツールで分けた音(stem)の取り込みも同じ扱いで用意する。
- **自前の学習は保留。** ドラムは、DSP による基準の実装(立ち上がり + 帯域でキック・スネア・ハイハットに振り分け)と、
  利用者が取得したモデルで扱う。分離・多楽器のモデルの学習も行わない。
- **モデルが無くても一通り動く。** 分離が無いときはミックスに直接 basic-pitch をかけ(精度は落ちる)、結果に確信の度合いを付けて返す。

### 11.2 処理の流れ

```
曲のファイル
  │ 読み込み(symphonia)・チューニングのずれの推定と補正
  ├─ 骨組み: Beat This! + DBN(移植)→ テンポマップ・拍子 / 構成(自己類似)/ 調(S-KEY)/ 和音(Jiang・consonance-ACE)
  ├─ 分離: 外部ツールで分けた stem の取り込み、または利用者が取得したモデル(無ければ省く)
  ├─ 譜起こし(stem ごと。stem が無ければミックスに直接)
  │    歌・ベース → SwiftF0 → 音符(音高は区間の中央値、揺れはピッチベンド)
  │    ピアノ → Transkun / Kong(強さ・ペダル。大きければ取得型)
  │    ギター・その他 → basic-pitch
  │    ドラム → DSP の基準の実装 + 後処理(開閉・強さ・ゴースト)/ 利用者が取得したモデル
  ├─ 統合: 拍への揃え(グリッド + ずれ量)、繰り返す区間で確率を平均、和音の転回形をベースで補強
  ├─ 音色: 楽器の系統に合う GM 音色・内蔵音源を割り当てる(合わせ込み・ミックスの逆算は後回し)
  └─ 確かめる: 書き出して原曲と比べ、観点ごとの差を AI と画面に返す → 直す
```

結果は `Command` を通して新しいトラック群として入れ、1 つのまとまりとして履歴に残す(丸ごと取り消せる)。
元の音声と取り込んだ stem は、参照用のトラックとして横に置く。

### 11.3 画面(7.2 節から)

1. 手順を「格子(テンポ・小節頭・拍子)→ 区間 → パート → 音符」の順にし、格子を最初に直せるようにする。
2. 起こした結果と原曲の瞬時の聴き比べ・重ね再生、音高を変えない遅い再生、拍に吸着する区間の繰り返し、パートの独奏を中心に置く。
3. 確信の低い音符は薄く描き、コードは候補から選ばせる。

## 12. 確かめるべき点

8. 法的な論点: 起こした MIDI を利用者が他の DAW に持ち出すこと、AI の API に曲の情報を送ること、編曲したカバーの公開の実務。

## 13. 実装と評価の記録

### 13.1 段階 0: 評価の仕組み(2026-10-14)

**考え方**: 実在の曲の正解(拍・和音などの注釈)は手元に無く、公開の評価セットも多くは音声を配っていないか非商用。
そこで、Glaux 自身で「正解の分かっている曲」を組み立てて書き出し、解析を当てて点数にする(8.3 節の方法)。
合成の曲は実在の録音より易しいので、数字は**方式どうしの比較と回帰の確認**に使い、実在の録音での確認は別に行う。

**作り**:

- 指標は `glaux_engine::mir_eval`。研究で広く使われる mir_eval・MIREX と同じ定義にして、論文の数字と比べられるようにした。
  - 拍・小節頭: 正解の ±70ms を当たりとする F 値。冒頭 5 秒は数えない。
  - テンポ: ±4% なら Acc1、倍・半分・3 倍・1/3 も許せば Acc2。
  - 調: MIREX の重み(同じ 1.0、5 度上下 0.5、平行調 0.3、同主調 0.2)。
  - 和音: 時間で重みを付けた一致率(WCSR)。根音 / 長短 / 長短 + 最低音(転回形)/ 四和音まで の 4 つの細かさ。
    正解がその語彙で書けない区間(長短のときの sus4 など)は分母から除く。
  - チューニング: ±50 セントで折り返した誤差。
  - ノリ: 8 分の裏の位置の誤差(% ポイント)、打ち込みか人の演奏かの見分けが合ったか。
- 曲の組み立てと集計は `crates/glaux-mcp/examples/recon_eval.rs`。曲は 24 小節で、次を乱数(種を固定)で散らす。
  - 編成: バンド(ドラム・ベース・和音・旋律)、ピアノ(ドラム無し)、電子(808 / 909 のキット・8 分のベース)。
  - 拍子(4 拍子 75%・3 拍子 25%)、調(短調 35%)、和音の進行(長調 10 種・短調 6 種。転回形・四和音・sus4 を含む)、
    和音の変わる間隔(1 小節に 1 つか、4 拍子なら 2 つ)。区間 A・B・A(8 小節ずつ)で進行を替える。
  - テンポ: 一定 / 途中で 8〜20% の段差 / 最後の 4 小節でだんだん 25% 遅く / 小節ごとに ±3% の揺れ。
  - 人の揺れ(拍の ±2.5%)、ハネ(8 分の裏を 56〜68% の位置へ)、チューニングのずれ(35% の曲で ±40 セント)、冒頭の無音(0.2〜1.5 秒)。
  - 音源: 半分を内蔵の音源、半分を GM の SoundFont(GeneralUser GS)で鳴らす。
    **訂正(13.9 節)**: 2026-10-15 まで、SoundFont のつもりの曲も内蔵の代わりの音で鳴っていた。13.2〜13.8 節の数字はすべて内蔵の音源の曲のもの。
- 調の正解は、主和音から始まり主和音を含む進行の曲にだけ付ける(vi から始まる進行などは平行調とも聞けるため)。
- 実在の録音の評価セットも `--dataset` で同じ指標にかけられる(音声と同じ名前の `.beats`〈時刻と拍の位置〉・
  `.lab`〈Harte の記法の和音〉・`.key`)。
- 再現: `cargo run --release -p glaux-mcp --example recon_eval -- --cases 24 --seed 1 --sf2 <GeneralUser-GS.sf2>`。
  `--beat minimal --chord perbar` で以前の方式、`--chord-sharp` などで和音の認識の設定を変えて比べられる。

### 13.2 段階 1: 曲の骨組みとノリの解析(2026-10-14)

入口は `glaux_mcp::recon::analyze`(モノラルの音声 → 骨組み)。段ごとの方式と、選んだ理由:

| 段 | 方式 | 置き場所 |
|---|---|---|
| 拍・小節頭・拍子 | Beat This!(同梱済み)の確率に、madmom の `DBNDownBeatTrackingProcessor` を移植して当てる(拍子 3・4 を別のモデルにして尤度で選ぶ) | `glaux_ml::dbn`、`glaux_ml::beats::track_dbn` |
| テンポの並び | 拍を最小二乗の直線でつなぎ、ずれが 45ms を超えたら区間を分ける | `recon::tempo_map` |
| チューニング | スペクトルの山の周波数(放物線で細かく)の、最寄りの半音からのずれを円周上で平均 | `glaux_engine::tonal::estimate_tuning` |
| 音の強さ | NNLS クロマ(Mauch と Dixon 2010): チューニングに合わせた 1/3 半音刻みの対数周波数のスペクトルを、1 オクターブの移動平均・標準偏差で白色化し、倍音を含む 88 鍵の音の形(h 倍音 0.7^(h-1))の非負の重ね合わせで説明する。拍ごとに平均してから分解する | `tonal::note_activations` |
| 和音 | 高音側のクロマを和音の形と余弦で比べ、低音側のクロマで最低音を確かめ、隠れマルコフモデル(ビタビ)でつなぐ。候補は 12 根音 × 長・短・7・maj7・m7・dim・aug・sus4 × 転回形 | `tonal::recognize_chords` |

### 13.5 段階 1 の画面側: 参考曲の聴き比べと遅い再生(2026-10-15)

**参考曲のトラック**: 参考曲は「参考」の印(`Track::reference`)を付けた音声トラックとして曲に置く(トラックを追加 →「参考曲を読み込む…」。
いちばん上に置き、曲の頭から)。印は `set_track_prop` の `reference` で付け外しでき、取り消せる。古い版の Glaux は印を知らないので、
ふつうの音声トラックとして開く(曲は壊れない)。

- 曲の音には混ぜない: 再生データ(`PlaybackData`)では、参考曲の音声クリップを曲のトラックとは別の並び(`reference`)に置く。
  書き出し・解析・トラックごとの書き出し・フリーズ・ミックスの点検・ゲームでは鳴らず、曲の長さにも入らない。
  ゲーム用の書き出しは参考曲のトラックを外し、その音声も写さない(配布物に他人の曲が入らないように)。
- 聴き方は 4 つ(`RefMode`): ふつう(参考曲は鳴らさない)/ 聴き比べの自分の曲 / 参考曲 / 重ねる。上の帯の「自分の曲・参考曲・重ねる」で
  切り替え、再生位置のまま約 10ms でなめらかにつなぐ(履歴の聴き比べと同じ作り)。参考曲はマスターのエフェクトとクリップ防止を通さない
  (仕上がった音のまま)。
- 音量をそろえる: 切り替えたとき、曲が変わっていれば、同じ範囲(ルーラーで選んだ区間か、参考曲の全体)の統合ラウドネスを測り直す。
  聴き比べでは大きい方を小さい方へ下げ(上げはしないので割れない)、重ねるときは参考曲を曲と同じ大きさにする(-24〜+6 dB)。
  市販の曲は打ち込み中の曲より大きいことが多く、デモ曲では参考曲を 6.1 dB 下げた。
- 読み込むと骨組み(13.2 節)を解析し、切り替えのボタンの吹き出しに要約(テンポ・拍子・調・テンポの揺れ・ノリ)を出す。

**遅い再生**: 100% → 75% → 50% のボタン(音程は変えない。聴く音だけで、書き出しには効かない)。
再生エンジンの出力の段で、流しながら伸ばす WSOLA(`glaux_dsp::varispeed`。40ms の窓を半分ずつ重ね、本来の位置の ±10ms から
直前の続きにいちばん似た所をつなぐ)をかける。曲を `速さ × 呼び出しの長さ` だけ描いてから伸ばすので、MIDI・音声・プラグイン・参考曲が
同じ速さで遅くなり、速さを変えても再生データを作り直さない。オーディオスレッドで使うので、メモリは作るときにだけ確保する。
テスト: 正弦波を 0.5・0.75 倍にして、長さが 1/速さ倍(誤差 8% 以内)・高さが同じ(±6Hz)・途切れが無いこと、半分の速さで参考曲が
倍の時間の後に 440Hz のまま鳴ること。

**画面の確かめ**: 1440〜800px の窓の幅で上の帯がはみ出さないこと(狭いときは切り替えの文字をしまい、800〜900px では
「参考曲」のボタンだけを残して押すたびに参考曲 ⇄ 自分の曲)、取り消し・やり直しで切り替えが出入りすること、英語の表示。
音そのもの(切り替えのつなぎ目・遅い再生の音質)は Windows の実機で聴いて確かめる。

### 13.6 段階 2: パートの譜起こしと作業場(2026-10-15)

### 13.10 段階 4: ドラムの譜起こし(2026-10-15)

**評価の足し方**: 評価用の曲のドラムのトラックだけを書き出し(分けた音)、正解の GM の番号を 4 種類(キック 35・36 / スネア・手拍子 37〜40 /
ハイハット 42・44・46 / シンバル 49・51・52・55・57・59)にまとめ、種類ごとに立ち上がりが ±50ms なら当たりとする F 値を出す
(`recon_eval --parts`。ドラムのある曲だけ)。曲そのものから起こしたときも同じ正解で測る。評価用の曲のドラムは、内蔵のドラム
(キット: modern・808・909)か、GM の SoundFont のスタンダードのキット。パターンはバンド(8 分のハイハット・2 拍 4 拍のスネア、
3 拍子もある)と電子(4 つ打ちのキックに手拍子)、区間の頭にクラッシュ。開いたハイハットは評価用の曲に無い。
調整は `cargo run --release -p glaux-engine --example drum_tune -- <フォルダ>`(`recon_eval` を `RECON_DRUMS=<フォルダ>` で流すと、
ドラムだけの音・曲そのものの音・正解を書き出す)。

**方式**: `glaux_engine::drum_transcribe`(信号処理だけ。学習したモデルは使わない)。短時間フーリエ変換(約 21ms、5ms 刻み)を
4 つの帯域(低 30〜150Hz・胴 150〜400Hz・響き 1.5〜5kHz・高 7〜16kHz)にまとめ、帯域ごとの「音の増え方」(スペクトル流束)の山を立ち上がりにする。

1. 高い帯域の山の余韻(20dB 下がるか、立ち上がりの前の大きさ + 3dB に戻るまで。下がり切る前に次の山が来たら、下がり方の速さから
   見積もる)。400ms を超えればシンバル、120ms を超えれば開いたハイハット、ほかは閉じたハイハット。
2. キックとスネアの候補: 低い帯域の山と、胴 + 響きの帯域の山(響きが高い帯域より目立つか、胴の音がはっきりある)。
   30ms 以内は 1 つに、余韻の中の山(直前の候補から 80ms 以内で全帯域が 6dB 以上小さい)は除く。
3. 候補の音の形(低 − 胴、低 − 響き の dB)を、曲の中で 2 つの群に分け(k 平均)、低い帯域が目立つ方をキックにする。
4. 同時に鳴った音: キックの群で、響きの帯域の大きさか余韻(40〜120ms 後)が「キックだけ」(群の下から 1/4)よりはっきり大きければスネアも、
   スネアの群で低い帯域がキックの群の中央値から 6dB 以内ならキックも。シンバルと同時ならスネアは足さない。
5. 分けていない曲そのものから起こすとき(`DrumOptions::mixed`)は、山の高さを上げ、帯域の最大から 10dB 以内の立ち上がりだけを候補にし、
   胴の音だけのスネアの候補と余韻で見るスネアを使わない。

**経緯**(種 2 の 14 曲で比べ、種 1・3 で確かめた。数字はキック / スネア / ハイハット / シンバル。分けた音から):

1. **帯域と決まった値**(低い帯域の山 = キック、胴 + 響きの山で響きが高い帯域より目立てばスネア、高い帯域の山 = ハイハット):
   内蔵 0.98 / 0.97 / 0.85 / 0.46、SoundFont 0.63 / 0.17 / 0.88 / 0.10。GM の生ドラムのキックは、打面の音で響きの帯域までスネアより大きく
   (立ち上がりの直後の大きさの平均で キック 28dB・スネア 21dB)、スネアの胴は低い帯域にも音があるため、スネアをキックと取り違えた。
   内蔵のキックは響きの帯域がほとんど無い(4.5dB)ので、決まった値では両方に合わせられない。
2. **NMF**(対数周波数 48 帯域の振幅を、キック・スネア・ハイハットの音の形と鳴り具合の積で近似。KL の乗法更新 40 回、形は初めの形へ
   半分引き戻す。Dittmar と Gärtner 2014 に倣う): 内蔵 0.75 / 0.69 / 0.69 / 0.03、SoundFont 0.45 / 0.59 / 0.94 / 0.38。
   初めの音の形が音色に合わないと崩れるので採らなかった。
3. **曲ごとの群分け**: SoundFont のスネアが 0.17 → 0.81、キックが 0.63 → 0.73。ただし内蔵のスネアが 0.97 → 0.75 に下がった
   (キックと同時のスネアがキックだけになる)。初めの中心に端の値を使うと、外れた 1 つが 1 群を独り占めした曲があった(キック 0.12)。
4. **同時に鳴った音の判定**と、初めの中心を上下 15% の所の値に: 内蔵 0.97 / 0.96、SoundFont 0.94 / 0.89。
   4 つ打ちのキックに毎回手拍子を重ねた曲では、重なった音がスネアの群になるので、スネアの群でも低い帯域が強ければキックも足す。
5. **山の高さ** 0.12 → 0.16(0.08〜0.25 を比べた。キック 0.966・スネア 0.938・ハイハット 0.917 で最も釣り合う)。
6. **種 1 で確かめると SoundFont のスネアが 0.58**。原因を 1 つずつ直した:
   - 曲の頭の無音からの立ち上がりで増え方(dB)が桁違いに大きくなり、山の高さの基準(増え方の最大)を独り占めしていた →
     帯域の大きさに底(最大 − 50dB)を付ける(種 2 の SoundFont のスネア 0.89 → 0.95)。
   - スネアとハイハットが同時だと、響きの帯域の最大はキックの打面の音なので、スネアの響きが高い帯域より小さく見えて候補から落ちた →
     胴の帯域がはっきりある(最大 − 15dB より大きい)ものも候補に(種 1 の SoundFont のスネア 0.68 → 0.79)。
   - GM のキックは立ち上がりの約 60ms 後にもう一度増え、2 つ目もキックとして数えていた → 余韻の中の山を除く(種 1 の SoundFont のキック 0.83 → 0.97)。
   - 4 つ打ちのキックに手拍子を重ねた曲では、キックの打面の音が大きく、重なった手拍子で響きの帯域の大きさがほとんど増えない →
     響きの帯域の余韻で見分ける(40〜120ms 後の平均 − 直後の最大: キックだけ -25dB、手拍子つき -3〜-14dB。種 1 の SoundFont のスネア 0.60 → 0.92)。
7. **シンバル**: 区間の頭のクラッシュがキックと重なると、シンバルの雑音でスネアと取り違え、クラッシュの後の 8 分のハイハットを
   クラッシュの響きごと長い余韻と見てシンバルにしていた → 高い帯域の余韻を先に測り(上の 1)、シンバルと同時ならスネアを足さない。
   SoundFont のシンバル 0 → 1.00。
8. **曲そのものから**: 上の調整で、分けた音からは良くなったが、曲そのものからはキック 0.70 前後 → 0.36 に下がった。
   ベース・和音の立ち上がりがキック・スネアの候補になり(推定 2507 に対し正解 312)、持続音で響きの余韻の判定も働いていた。
   本当の打音は強く(帯域の最大から 10dB 以内)、ほかの楽器の立ち上がりは弱いので、曲そのもの用の設定(上の 5)を分けた。

既定のパート(省略時)にも入れた。今の曲に取り込むとき(13.8 節)、ドラムは移調しない(打楽器の番号なので)。合成の参考曲でドラムだけを起こすと、内蔵のドラムのトラックに 1095 音が入った(画面で確かめた)。

**分かっている弱点**:

- 内蔵のクラッシュは立ち上がりの直後に急に小さくなる音色で、ハイハットと見分けられない(シンバルが 0.03。1 曲に 2 回ほど)。
- 内蔵のスネアは高い帯域の音も大きく、スネアと同時のハイハットを拾えない(内蔵のハイハットの見落とし)。
- 曲そのものからは、SoundFont のスネアが 0.35(キックの打面の音とほかの楽器に埋もれる)。分けた音から起こすのが前提。
- 開いたハイハット・タム・ライド・強さ(ベロシティ)は評価していない。ゴーストノート(弱い打音)は、曲そのものからでは拾わない。
